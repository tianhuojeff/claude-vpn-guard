# 故障响应时间报告（V2.1，2026-11-01）

原始数据：`evidence-bench-20.txt`（原始输出未随公开版发布）（每次注入的全部时间戳）、`evidence-lab.txt`（原始输出未随公开版发布）。

## 测量方法

- **环境**：真实 Mihomo 内核（verge-mihomo v1.19.32，独立的私有实例）+ 本机假节点（可模拟卡死、断线、变慢）+ 节点管理器 + 保护引擎。防火墙和 Claude 用模拟实现，只用来记录“锁定”“结束”动作发生的时刻。
- **参数**：全部用默认值，**探测超时没有缩短**：单次探测超时 3000ms，连续失败 2 次，延迟上限 300ms。旧策略检测周期 3s，新策略存活探测间隔 1000ms。
- 每种情况各测 **20 次**。每次注入故障前随机等待 0～3 秒，避免故障时刻总是和探测周期对齐。
- 所有时间都是**相对故障注入时刻**的毫秒数。

## 一、关键区分：发现耗时 ≠ 真实 IP 泄漏窗口

| | 含义 | 本报告的数据 |
|---|---|---|
| 故障发现与切换耗时 | 节点坏了以后，多久能换到好节点 | 下面各表 |
| 真实 IP 泄漏窗口 | 这段时间里 Claude 有没有可能直连 | 隔离模式下，Claude 的出口由专用入口（`listener.proxy`）固定。节点坏掉时，Claude 的请求**只会失败，不会直连**（真实 Mihomo 实验验证）。WFP 持久过滤器全程不变（测量中断言“静态规则未被改动”，20/20）。WFP 本身对 Claude 的拦截效果**待 selftest 实测** |

所以，节点故障期间的几秒，代表的是 Claude “暂时连不上”，而不是“可能泄漏”。

## 二、卡死（探测超时）：修改前后对比（各 20 次）

| 阶段 | 修改前·串行 平均 / 最大 / P95 | 修改后·流水线+并行预检 平均 / 最大 / P95 |
|---|---|---|
| 首次发现 | 4265 / 5888 / 5849 | 3575 / 3997 / 3903 |
| 二次确认 | 8276 / 9905 / 9866 | 4583 / 5013 / 4911 |
| 候选节点检测 | 确认之后才开始（约 +160ms） | 首次失败时**并行**开始，确认前已完成（复用） |
| 开始切换 | 8276 / 9905 / 9866 | 4583 / 5013 / 4911 |
| **切换完成（可用）** | **8501 / 10133 / 10091** | **4644 / 5079 / 4979** |
| 故障转移本身（完成 − 确认） | 224 / 245 / 231 | 62 / 71 / 68 |

**探测超时和整个故障转移耗时是分开的：**
- 首次发现：发起探测最多再等 1s，加上 3s 超时，所以下限约 3s，这是“没有缩短超时”的直接结果。
- 二次确认：下一个流水线探测比上一个晚 1s 发起，所以确认时间约等于首次发现 + 1s。
- 故障转移本身（选中 → 出口验证 → 路径验证）只有约 60ms，因为候选节点已经预先测好。
- 修改前慢在两处：串行等待“下一个周期 + 再一次超时”（3s + 3s），以及确认之后才开始测候选节点。

## 三、断线（连接被拒）：修改前后对比（各 20 次）

| 阶段 | 修改前 平均 / 最大 / P95 | 修改后 平均 / 最大 / P95 |
|---|---|---|
| 首次发现 | 1626 / 2885 / 2543 | 506 / 961 / 911 |
| 二次确认 | 4651 / 5914 / 5575 | 506 / 961 / 912 |
| 开始切换 | 4651 / 5914 / 5575 | 506 / 961 / 912 |
| **切换完成（可用）** | **4874 / 6143 / 5805** | **732 / 1188 / 1131** |
| 故障转移本身 | 223 / 231 / 231 | 225 / 230 / 229 |

注意：连接被拒时，“立即复检”在约 1ms 内就完成了二次确认，所以二次确认几乎和首次发现同时发生。代价见第六节。

## 四、全部日本节点失败：安全阻断时间线（20 次，修改后）

| 阶段 | 平均 / 最大 / P95（ms） |
|---|---|
| 首次发现 | 514 / 975 / 902 |
| 判定全部失败 | 517 / 977 / 906 |
| 网络阻断（锁定） | 517 / 977 / 906 |
| Claude 结束 | 517 / 977 / 906 |

20/20 次都是先锁定，再结束 Claude；20/20 次专用入口都没有回退到直连或其他国家节点。

## 五、Mihomo 内核被强制结束

| 阶段 | 实测 |
|---|---|
| 发现 | 9～11ms（进程句柄等待，由事件触发，不靠轮询） |
| 锁定 | 11～12ms |
| Claude 结束 | 11～13ms |

内核退出后，专用入口无法再连接，不存在回退路径。

## 六、网络抖动下是否误杀 Claude（各 40 秒，Claude 运行中）

| 抖动类型 | 探测次数 | 切换 | 锁定 | 误杀 Claude |
|---|---|---|---|---|
| 偶发失败（每两次请求失败一次） | 78 | 0 | 否 | 否 |
| 延迟尖峰（100～450ms 随机） | 42 | 0（受最短驻留 120s 约束） | 否 | 否 |
| 短暂断线（每 5 秒断 700ms） | 41 | **1** | 否 | 否 |

结论：三种抖动都**没有误杀**，也都**没有锁网**。短暂断线引发了 1 次节点切换，原因是“立即复检”对连接被拒类故障太敏感。之后不再来回切换，因为故障节点会被隔离 300 秒。如果希望更抗抖，可以在 GUI 里把“连续失败次数”改为 3，代价是断线切换会慢约 1 秒。

## 七、对照性能目标

| 目标 | 实测（修改后） | 是否达成 |
|---|---|---|
| 内核退出 1 秒内发现 | 约 10ms | 达成 |
| 安全异常尽快阻断 | 全部失败：判定后 0～2ms 内锁定 | 达成（模拟防火墙；真实 WFP 下发耗时待实测） |
| 节点故障 3～6 秒内启动切换 | 卡死：平均 4.6s，最大 5.0s；断线：平均 0.5s，最大 1.0s | 达成 |
| 恢复验证通过后立即更新状态 | 路径验证完成 → 标记可用 < 1ms | 达成 |
