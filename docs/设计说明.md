# 设计说明与已知限制

## 1. 第一阶段技术验证结论（本机实测，2026-11-01）

| 项 | 实测结果 |
|---|---|
| Clash Verge | `C:\Program Files\Clash Verge\clash-verge.exe`（GUI）+ `clash-verge-service`（系统服务）+ `verge-mihomo`（内核，由服务以高权限拉起） |
| 内核控制接口 | **命名管道** `\\.\pipe\verge-mihomo-production-<hash>`；TCP 控制口默认关闭（`external-controller: ''`）。配置里写的管道名（`...sidecar-release-...`）与实际运行的不一致 → 必须枚举系统管道自动发现，不能写死 |
| 内核版本 / 模式 | Mihomo v1.19.32，当时为全局模式 + 系统代理（127.0.0.1:7897），TUN 关闭；`dns.enhanced-mode: fake-ip`，`fake-ip-range: 198.18.0.1/16` |
| 连接元数据 | 系统代理模式下 Mihomo 连接的 `process/processPath` **为空**（只有 TUN 才有）→ 改用「本地源端口 → TCP 表反查 PID」来识别哪条连接属于 Claude |
| 嗅探 | Mihomo 收到 TLS ClientHello 后才拨号并登记连接 → 探测必须先完成 TLS 握手，连接保持期间再查路由 |
| Claude 桌面版 | MSIX 包 `AnthropicPBC.Claude_fnn82j28hfe8t`，主程序 `...\app\claude.exe`（启动入口 `shell:AppsFolder\AnthropicPBC.Claude_fnn82j28hfe8t!Claude`）；内置 Claude Code 在 `%LOCALAPPDATA%\Claude-Data\...\claude-code\<版本>\<hash>\claude.exe`，**每次更新路径都变** |
| 签名 | 上述 exe 均为有效 Authenticode 签名，签名者 `O="Anthropic, PBC"` → 用「安装目录 + 签名」双重核实身份，不凭进程名 |
| 防火墙 | 三个配置文件均启用，默认出站允许 |
| 构建环境 | 无 .NET SDK，只有运行时 → 采用 Windows 自带的 .NET Framework 4.8 + 系统 csc 编译，**零依赖、零下载** |

## 2. 网络路径分析：谁发起了什么连接

```
系统代理模式：  Claude.exe ──TCP──▶ 127.0.0.1:7897 ──▶ verge-mihomo.exe ──▶ 远程节点(VLESS) ──▶ Anthropic
                  (回环)                                 (Mihomo 发起真实出站)
TUN 模式：      Claude.exe ──TCP/UDP──▶ 198.18.x.x(fake-ip) ──▶ Wintun 网卡 ──▶ verge-mihomo.exe ──▶ 远程节点
                  (DNS 被劫持，返回 fake-ip)
泄漏路径：      Claude.exe ──▶ 真实 IP（Clash 没开 / 系统代理被关 / 回退 DIRECT / IPv6 / QUIC / 自带 DoH）
                Claude.exe ──▶ 127.0.0.1:7897 ──▶ Mihomo 按 DIRECT 规则直连（模式=直连 / 规则命中 DIRECT / 组选了 DIRECT）
```

关键结论：
- **不能**简单阻断 Claude 全部出站：系统代理模式下 Claude 本身只连回环；TUN 模式下只连 fake-ip。所以规则是「阻断 Claude 去往 回环 和 fake-ip 以外的一切」，Mihomo 自己的出站完全不受影响。
- 第一类泄漏（Claude 直接连真实 IP）由**持久防火墙规则**在内核层拦截，与保护器是否在运行、检测快慢无关。
- 第二类泄漏（Mihomo 替 Claude 直连）防火墙无法区分（出站连接是 Mihomo 发起的，且 Windows 防火墙对回环豁免），只能**检测 + 结束进程**：每 2 秒检查模式、全局出站链、Claude 每条真实连接的出站；每 60 秒做真实探测。

## 3. TUN 与系统代理：安全等级

| 模式 | Claude 直连真实 IP | Mihomo 替 Claude 走 DIRECT | 等级 |
|---|---|---|---|
| TUN（fake-ip） | 防火墙阻断（预防性） | 检测后锁定：锁定规则能阻断 Claude→fake-ip（非回环），**锁定立即生效** + 结束进程 | **高** |
| 系统代理 | 防火墙阻断（预防性） | 检测后结束进程；锁定规则对回环无效，期间（≤2 秒轮询间隔）Claude 的既有连接可能经 DIRECT 发出 | **中** |
| 两者同开 | 同 TUN | 同系统代理（Claude 优先用系统代理） | 中 |

**建议使用 TUN 模式**（并保持 `enhanced-mode: fake-ip`）。注意：TUN 若用 redir-host（真实 IP），Claude 的流量目的地是真实 IP，会被静态规则拦下导致 Claude 无法联网——这是故障安全的表现，不是泄漏。如要放行别的 fake-ip 段，由管理员改 `settings.json` 的 `FakeIpRange`。

仅系统代理模式可通过管理员把 `AllowSystemProxyMode` 设为 `false` 禁用（之后只有 TUN 有效时才放行）。

## 4. 架构

```
ClaudeVPNGuard.Service.exe  (LocalSystem 服务, 开机自启, 崩溃自动重启)
 ├─ WindowsFirewall   持久规则：Static-<路径哈希>（永久） + Lock-<路径哈希>（按状态启停），规则组 ClaudeVPNGuard
 ├─ ClaudeLocator     扫描 WindowsApps / Claude-Data / AnthropicClaude + 运行中进程；路径+Anthropic 签名核实
 ├─ MihomoClient      枚举命名管道 / 配置中的 TCP 控制口，secret 只在内存，HTTP/1.0 只读查询
 ├─ HealthChecker     防火墙、内核、模式、出站链、连接审计、TCP 表审计、TUN/系统代理、真实探测、出口 IP(仅展示)
 ├─ GuardEngine       状态机：Verifying / Protected / Blocked / Tripped / FirewallError
 ├─ 事件              WMI 进程启动、网络地址变化、休眠/恢复、会话登录/注销/解锁
 └─ IpcServer         命名管道，ACL=SYSTEM/管理员/交互用户；改状态命令只接受安装目录下的 ClaudeVPNGuard.exe
ClaudeVPNGuard.exe          (普通权限 GUI + 托盘)  状态/日志/设置；修复与卸载经 UAC 调用服务程序
```

状态与动作：

| 事件 | 动作 |
|---|---|
| 服务启动 / 重启 | 先建/启用锁定规则 → 验证 → 通过才解锁；上次触发过保护且未手动解锁 → 保持「Claude 已阻断」 |
| 关键检测失败 + Claude 在运行 | 锁定 → 结束 Claude 全部进程树 → 通知 → 日志 → 状态「Claude 已阻断」 |
| 仅「探测超时/测速失败」（可能是抖动） | 第一次：立即锁定、不结束进程、马上复检；连续第二次：保护性关闭 |
| 关键检测失败 + Claude 未运行 | 锁定，状态「代理异常」 |
| 网络切换 / 休眠恢复 / 会话变化 | 锁定 → 等 1.5 秒网络稳定 → 完整验证 → 通过才解锁 |
| 非「已保护」状态下 Claude 启动 | 「检测中」：保持锁定并立即复检；其余状态：立即结束 + 通知 |
| 出现未纳入规则的新 Claude 程序（如自动更新） | 立即补建规则；若当时不安全则结束该进程 |
| 保护器内部异常 | 锁定（故障安全） |
| 服务被停止 | 锁定规则保持启用，不删除任何规则 |

## 5. 故障安全要求对照

| 要求 | 实现 |
|---|---|
| 保护器崩溃时规则仍生效 | 规则是 Windows 防火墙持久规则，与进程无关；未处理异常处理器会再启用一次锁定 |
| Clash Verge 崩溃时规则仍生效 | 静态规则永久生效；内核不可达 → 锁定 + 关闭 Claude |
| 重启后验证前不直连 | 静态规则开机即生效；锁定规则保持上次状态（停止/关机时总是启用） |
| 关闭 GUI 不移除规则 | GUI 不持有任何规则，也没有「关闭保护」的命令 |
| 普通进程不能解除保护 | 规则修改需管理员；IPC 无解除命令；解锁只能经完整检测 |
| 不静默关闭防火墙 / 不碰无关规则 | 只读防火墙开关状态；只增删规则组 `ClaudeVPNGuard` 的规则 |
| 管理员恢复机制 | `recover` 命令；兜底 PowerShell 一行命令 |
| 最小影响 | 规则只作用于核实过的 Claude 可执行文件；微信/QQ/浏览器/Windows Update 不受影响 |

## 6. 已知限制（不夸大）

1. **回环豁免**：Windows Defender 防火墙不过滤回环流量，所以锁定规则拦不住 `Claude → 127.0.0.1:代理端口`。系统代理模式下「Mihomo 把 Claude 流量走 DIRECT」只能靠 ≤2 秒的轮询检测 + 结束进程，存在短暂窗口。要彻底解决需要自研 WFP 驱动级过滤器（带权重高于回环豁免的持久 WFP filter），当前版本未实现。**用 TUN 模式可避开这个限制。**
2. **规则模式下的路由判断**依赖真实探测（api.anthropic.com）和对 Claude 实际连接的审计。按进程名写的规则（PROCESS-NAME）无法用探测覆盖，只能靠连接审计发现。探测本身是一次经 Mihomo 的 TLS 握手；如果规则把该域名路由到 DIRECT，这一次握手本身会直连（不携带任何账号信息），随后立即阻断 Claude。
3. **Claude Code 派生的通用程序**（git、node、curl、bash 等）不是 Anthropic 签名的程序，无法单独加防火墙规则（否则会影响你在别处使用它们）。保护触发时它们作为 Claude 子进程树一并被结束；但正常运行时若它们自己直连（不走系统代理），保护器不拦。
4. **Claude 的 Hyper-V 虚拟机（cowork / claude-code-vm）**：虚拟机流量经 Windows NAT 发出，不归属于 Claude.exe，防火墙按程序路径无法约束；触发保护时随 Claude 进程结束而停止联网，但不保证。
5. **服务被管理员停止**期间只剩静态规则 + 锁定规则（停止时已启用），没有检测；系统代理模式下 DIRECT 风险不被监控。
6. **结束进程用强制方式**：服务运行在 Session 0，无法给桌面窗口发正常关闭消息；而且网络已先锁定，速度优先。
7. **新版本 Claude 首次启动**：若更新后的程序在 2 分钟重扫之前、且保护器非「已保护」时启动，会被结束一次，重新打开即可。
8. 出口 IP 只做展示，不作为安全依据（经代理访问 `www.cloudflare.com/cdn-cgi/trace`，每 10 分钟最多一次，可在设置里关闭）。
9. 不修改 Clash Verge 的任何订阅、节点、配置。

## 7. 隐私

日志位于 `C:\ProgramData\ClaudeVPNGuard\logs`，按天分文件，默认保留 14 天。只记录状态、模式、节点名、规则变化、动作结果；**不记录**对话内容、密码、API Key、控制接口 secret、订阅链接、节点认证信息（另有兜底脱敏：Bearer token、`secret:`、UUID）。程序不上传任何数据。

# V2 设计（2026-11-01，updated_by: claude-code）

## V2.1 V1 安全问题的结论

V1 的系统代理模式里，Claude 先连本机代理端口，再由 Mihomo 按模式/规则决定出站。如果 Mihomo 把这些流量走成 DIRECT，防火墙既看不到也拦不住：一是这些连接是 Mihomo 发起的，二是 Windows 防火墙豁免回环流量。V1 只能靠检测后结束进程，**中间存在时间窗口**。

V2 的解决思路是不再去“追”Mihomo 的路由决定，而是把 Claude 的出口在结构上固定住：

1. **专用入口**：通过 Clash Verge 全局扩展脚本新增 listener `127.0.0.1:17897`，设置 `proxy: Japan Auto`。Mihomo 对带 `proxy` 的入站流量使用 `SpecialProxy`，**优先于模式和规则**。这一点已在真实 Mihomo v1.19.32 上实验验证：direct 模式、GLOBAL 选 DIRECT 或韩国节点、规则 MATCH,DIRECT 时，专用入口仍然只走日本节点。
2. **Japan Auto 组**：select 类型，只含日本节点（自动识别 + 手动包含 − 手动排除），不含 DIRECT。没有日本节点时组内只有 REJECT。
3. **WFP 强制**：自有 provider + 子层（权重 0xFFFF），在 `ALE_AUTH_CONNECT_V4/V6` 层为每个 Claude 程序（AppId 条件）下发**持久过滤器**：阻断 Claude 连接回环上的通用代理端口；阻断一切非回环地址（覆盖 TCP 和 UDP，即 QUIC/DNS）；只允许回环的其他端口。锁定时再加一条阻断全部的过滤器。
4. **带参数启动 Claude**：通过 MSIX 应用激活接口传入 `--proxy-server=http://127.0.0.1:17897`。如果 Claude 不接受这个参数，WFP 会让它根本无法联网，而不是直连。

需要实测的两点：WFP 能否真正拦住回环连接（`selftest` 的 W4/W5 用例），以及 Claude 是否接受启动参数。在实测之前，文档中一律标为**未验证**。详见 [已知安全限制.md](已知安全限制.md)。

## V2.2 持久过滤器与动态过滤器

| 类型 | 生命周期 | 本程序用法 |
|---|---|---|
| 动态过滤器（未设 PERSISTENT 标志，或建立在动态会话中） | 创建它的引擎会话关闭（进程退出或崩溃）时自动消失 | **不使用** |
| 持久过滤器（`FWPM_FILTER_FLAG_PERSISTENT`，provider 和子层也是持久的） | 存储在 BFE 中，进程退出、服务崩溃、重启后都继续存在，直到被显式删除 | 全部过滤器都用持久类型 |
| 启动时过滤器（BOOTTIME） | 只在 BFE 启动前生效 | 不使用；重启早期的窗口见限制第 6 条 |

`selftest` 阶段 3 的做法是：先由一个子进程下发过滤器，再强制结束这个子进程，然后测试过滤器是否仍然生效，以此证明“不是随会话消失的动态过滤器”。`audit` 会逐个列出过滤器，并标注它是“持久”还是“动态”，以及是否带有程序条件。

## V2.3 节点故障转移

- 故障分级：
  - **安全故障**：组缺失、组内出现非日本节点、隔离被绕过、内核退出、全部日本节点失败。处理顺序是锁定 → 结束 Claude → 通知。
  - **节点/质量故障**：只切换节点，不锁网，不结束 Claude。在隔离模式下节点不可用时 Claude 只会连接失败，不可能直连。
- 当前节点监控（V2.1 流水线）：
  - 每秒发起一次存活探测，最多 4 个并发，单次超时固定 3 秒（不缩短）。
  - 结果按发起顺序判定。
  - 首次失败后立即追加复检，同时并行预检其他日本节点；确认故障时直接复用预检结果。
- 选择与验证流程：延迟 ≤ 上限，按延迟排序 → 切换 → 经专用入口查询出口国家必须为 JP → 经专用入口建立连接，核对 Mihomo 记录的 `specialProxy=Japan Auto` 且出站就是所选节点 → 才标记为可用。
- 防抖措施：
  - 连续失败计数
  - 恢复需要连续成功
  - 切换冷却 30 秒
  - 最短驻留 120 秒（只约束质量故障）
  - 故障节点隔离 300 秒
  - 切换状态锁
  - 当前节点健康时，不会因为其他节点更快而切换
- 全部节点失败：锁定并结束 Claude；不回退 DIRECT，也不使用其他国家节点；每 60 秒重试；恢复后发通知，等待你手动启动 Claude。
- Mihomo 内核退出：用进程句柄等待来检测，属于事件驱动（实测约 10ms 发现）。
