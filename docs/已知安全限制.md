# 已知安全限制清单（V2）

> 原则：只陈述验证过的能力；未验证的标注“未验证”；无法解决的列在这里，不隐瞒。

## A. V2 的安全模型（隔离模式）

```
Claude.exe ──(WFP 只允许)──▶ 127.0.0.1:17897 专用入口 ──(listener.proxy 固定)──▶ Japan Auto(仅日本节点) ──▶ 远程节点
     │
     ├─✘ 127.0.0.1/::1 上的通用代理端口(7897/7898/7899/7890/7891…)   ← WFP 权重12 阻断
     ├─✘ 任何非回环地址 IPv4/IPv6，TCP/UDP（含 QUIC、自带 DNS/DoH）    ← WFP 权重1 阻断 + Windows 防火墙静态规则
     └─✔ 回环其他端口（本机服务、Claude 自身组件通信）                   ← WFP 权重10 允许
```

| 结论 | 证据等级 |
|---|---|
| 经专用入口的流量**不受模式/规则/GLOBAL 影响**：direct 模式、GLOBAL 选 DIRECT、GLOBAL 选韩国、规则 MATCH,DIRECT 时仍只走 Japan Auto | 真实 Mihomo v1.19.32 实验（`evidence-lab.txt` E1） |
| Japan Auto 组内只有日本节点，无法通过 API 被切到 DIRECT 或他国节点；无日本节点时只含 REJECT | 真实 Mihomo 实验 |
| 当前节点失效/全部失效时，专用入口请求直接失败，不回退直连或其他节点 | 真实 Mihomo 实验（S3、S12、全部失败 ×20） |
| Claude 无法绕过专用入口（连不上通用端口、连不上任何公网地址） | **未验证**——依赖 WFP 对回环的实际执行效果，需 `selftest` 实测 |

## B. 剩余风险（无法或尚未消除）

1. **WFP 回环控制尚未实测**。Windows 防火墙规则对回环流量豁免；我们改用自有 WFP 子层（最高子层权重）在 `ALE_AUTH_CONNECT` 层阻断 Claude→通用代理端口。这是否被系统执行，**只有 `selftest` 的 W4/W5 用例能证明**。若实测失败（回环未被拦），隔离模式降级为：Claude 若自行使用系统代理 7897，仍可能经 Mihomo 规则走 DIRECT，此时只剩 V1 的检测 + 结束进程（≤2 秒窗口）兜底。
2. **Claude 是否接受 `--proxy-server` 参数尚未验证**。保护器通过 MSIX 应用激活接口带参数启动 Claude。若 Claude 忽略此参数而使用系统代理：在 WFP 回环控制生效的前提下，结果是 **Claude 无法联网（故障安全）**，不会直连；需你授权后实测（要退出当前 Claude）。
3. **Claude 内置 Claude Code 等子进程**：Anthropic 签名的 exe（含 `claude-code\…\claude.exe`、`cowork-svc.exe` 等）都受同样的 WFP 过滤器约束；但它们派生的通用程序（git、node、bash、curl）不是 Anthropic 签名，无法按程序单独限制（否则会影响你在别处使用）。保护触发时作为子进程树一并结束；正常运行时若它们自行直连，本程序不拦。
4. **Mihomo 自身的出站**：WFP 只约束 Claude 程序，不约束 Mihomo。专用入口的 `proxy: Japan Auto` 由 Mihomo 执行；若有人修改覆写脚本把 listener 改成别的出站，或 Mihomo 自身缺陷，Claude 流量的去向就由 Mihomo 决定。缓解：每 60 秒经专用入口做一次真实探测，核对 Mihomo 记录的 `specialProxy=Japan Auto` 与出站节点；Claude 每条连接都审计 `specialProxy`，缺失即判定隔离失效并保护性关闭。这是**检测**而非预防。
5. **节点自身 DNS**：Mihomo 解析代理服务器域名、以及系统 DNS 客户端（svchost）代 Claude 做的解析，不归属 Claude 程序，WFP 无法按程序约束。经专用入口时 Chromium 把域名交给代理，不在本地解析；但若 Claude 某组件调用系统解析，查询的域名可能经系统 DNS 发出（不含账号数据，暴露的是“查询了 anthropic 相关域名”）。
6. **重启窗口**：WFP 持久过滤器在 BFE 服务启动时加载。BFE 启动前系统按 Windows 默认启动时策略处理网络；在此期间 Claude 通常尚未启动。**重启持久性未验证**，需 `selftest --keep` → 重启 → `selftest --after-reboot`。
7. **Claude 的 Hyper-V 虚拟机（cowork / claude-code-vm）** 流量经 Windows NAT 发出，不归属于 Claude 程序，WFP 按程序无法约束。
8. **短暂断线会触发一次节点切换**：首次失败后立即复检，对“连接被拒”类故障，二次确认在约 1ms 内完成，所以 700ms 级别的短暂断线会导致一次切换（实测不锁网、不结束 Claude）。这是“快速切换”与“抗抖动”的取舍；可在 GUI 中把“连续失败次数”调到 3 降低敏感度。
9. **非隔离模式（V1 兼容模式）**仍有 V1 的限制：系统代理模式下“Mihomo 把 Claude 走成 DIRECT”只能检测后结束进程。V2 不再推荐该模式。
11. **环境变量代理**：本机用户环境变量 `HTTP(S)_PROXY/ALL_PROXY=127.0.0.1:7897`，Claude Code 会读取。隔离模式下这会让 Claude Code 无法联网（故障安全，不泄漏）；本程序**不修改**这些用户环境变量；可选 `cc-proxy apply` 只在 Claude Code 自己的 settings.json 的 env 中指向专用入口。Claude Code 的 settings env 是否优先于进程环境变量，**尚未在真实 Claude Code 上验证**。
12. **本机其他代理**：隔离模式允许 Claude 连接回环上的“其他端口”（为了不破坏本地 MCP、IDE 集成等）。本程序会把代理类进程（clash、mihomo、v2ray、xray、sing-box 等）监听的端口自动加入阻断名单；但对不认识的代理程序，或者自行开启本地转发的程序，无法识别。
13. **spacedesk**：本程序不放行任何局域网流量，也不触碰 spacedesk。“传输期间不断开”只能在扩展屏连接时实测，当前未验证。
10. **出口国家校验**依赖 Cloudflare trace 的地理位置判断，只用于拒绝明显错误的节点，不作为唯一安全依据。

## C. 不会做的事

- 不修改 GLOBAL 或任何其他代理组、订阅、节点；只新增 Japan Auto 组、一个专用 listener 与规则最前面的 Claude 专用规则。
- 不改系统默认防火墙策略，不添加任何不带程序条件的过滤器（`audit` 会逐个证明），不影响 spacedesk 等局域网软件。
- 不静默关闭防火墙，不删除别人的规则。
